# ssc32_ros2_control

[![CI](https://github.com/MartinPeris/ssc32_ros2_control/actions/workflows/ci.yml/badge.svg)](https://github.com/MartinPeris/ssc32_ros2_control/actions/workflows/ci.yml)
[![License: BSD-3-Clause](https://img.shields.io/badge/License-BSD--3--Clause-blue.svg)](LICENSE)

A position-only `ros2_control` hardware component for Lynxmotion SSC-32 and
SSC-32U servo controllers. It delegates all wire-protocol and serial I/O to the
standalone [ssc32](https://github.com/MartinPeris/ssc32) C++ library.

## Status

Configuration parsing, calibration conversion, command batching, communication
failures, and the real POSIX serial path are covered by automated tests on ROS 2
Lyrical. A controller-manager integration test executes a standard
`FollowJointTrajectory` action through the plugin and a stateful SSC-32
emulator. Physical controller and servo validation is pending.

## Design

The plugin represents one SSC-32 board as one
`hardware_interface::SystemInterface`. Every configured joint exposes a
`position` command interface and a `position` state interface. Commands for all
joints are converted to pulse widths, validated, and sent in one SSC-32 command.

The standard `joint_trajectory_controller` performs trajectory interpolation.
The driver deliberately does not translate trajectory segments into SSC-32
timed moves. An optional per-joint SSC-32 speed value provides a separate pulse
slew-rate ceiling.

See [ARCHITECTURE.md](ARCHITECTURE.md) for lifecycle and failure behavior.
See [TESTING.md](TESTING.md) for test boundaries and the serial timing envelope.

## Configuration inspection

`ssc32_config_inspect` validates a URDF without opening the serial device. It
uses the same parser and calibration checks as the hardware plugin, then reports
the resolved channel map, position limits, pulse envelopes, endpoint pulses,
direction, scale, and slew ceiling.

```sh
ros2 run ssc32_ros2_control ssc32_config_inspect robot.urdf
ros2 run ssc32_ros2_control ssc32_config_inspect --json robot.urdf
ros2 run ssc32_ros2_control ssc32_config_inspect --hardware arm_board robot.urdf
```

`--hardware` is required only when a URDF contains more than one SSC-32 hardware
component. Exit status is nonzero for malformed, ambiguous, or unsafe
configuration, making the command suitable for commissioning scripts and CI.

## Diagnostics

The hardware component publishes a bounded status through the standard
`/diagnostics` topic using `diagnostic_updater`. Its hardware ID is
`ssc32:<device>` and the task is `Communication`.

Summary levels have operational meaning:

- `OK`: connected and inactive, or active with a recent successful pulse query.
- `WARN`: not configured, or active but still waiting for its first read.
- `STALE`: active without a successful read inside the staleness threshold.
- `ERROR`: connection, read, write, cancel, or lifecycle failure.

The status includes firmware, lifecycle state, joint count, cumulative read and
write/error counters, transmitted versus suppressed writes, last/max serial
latencies, read age, and the last failed operation. It deliberately does not
claim measured servo position or mechanical health.

`diagnostics_stale_after_ms` is an optional hardware parameter. If omitted, it
defaults to the greater of 1000 ms or four times `timeout_ms`. Publication uses
the standard `diagnostic_updater.period` parameter and defaults to 1 Hz.

## Feedback limitation

SSC-32 `QP` queries report the pulse generated by the controller, not measured
servo-shaft position. Published joint state is therefore an output-position
estimate. It cannot detect a stalled servo, collision, stripped gear, or slipped
linkage. This package is not a safety system.

## Workspace build

ROS 2 Lyrical and the `ros2_control` development packages are required.

```sh
mkdir -p ws/src
git clone https://github.com/MartinPeris/ssc32_ros2_control.git ws/src/ssc32_ros2_control
vcs import ws/src < ws/src/ssc32_ros2_control/ssc32.repos
cd ws
source /opt/ros/lyrical/setup.bash
colcon build --packages-select-up-to ssc32_ros2_control
colcon test --packages-select ssc32 ssc32_ros2_control
colcon test-result --verbose
```

## Hardware configuration

The plugin is configured inside the robot's `<ros2_control>` element. Board
parameters belong under `<hardware>`:

- `device`: serial device path.
- `baud_rate`: controller baud rate, normally `115200`.
- `timeout_ms`: bounded serial response timeout.
- `diagnostics_stale_after_ms`: optional threshold for stale-read diagnostics.

Each joint requires exactly one double `position` command interface with
explicit `min` and `max`, and one double `position` state interface. Joint
parameters are:

- `channel`: unique SSC-32 channel, 0–31.
- `zero_pulse_us`: pulse at zero joint position.
- `pulse_us_per_unit`: pulse change per radian or metre.
- `direction`: `1` or `-1`.
- `min_pulse_us` and `max_pulse_us`: hard conversion envelope.
- `max_speed_us_per_second`: optional SSC-32 pulse slew-rate limit.

The conversion is:

```text
pulse_us = zero_pulse_us + direction * position * pulse_us_per_unit
```

The position limits and pulse envelope are both checked during initialization
and again before every command. See [urdf/example.urdf](urdf/example.urdf) and
[config/controllers.yaml](config/controllers.yaml).

## Safe commissioning

1. Keep servo power disconnected and configure the component to verify firmware
   identification and pulse queries.
2. Confirm every physical channel independently.
3. Calibrate zero, direction, scale, and narrow pulse limits with the linkage
   unloaded.
4. Enable one joint at a time with an accessible power cutoff.
5. Add the trajectory controller only after direct position commands are
   repeatable.

Activation samples the board's current pulse outputs and seeds both state and
command interfaces from them. It never sends an automatic home movement.
